# 구조

에코 왕복이라는 최소 도메인 위에 **네트워크 · 비동기 · DB** 세 계층을 얹었다.
기능을 늘리는 대신 계층의 경계와 그 경계에서 감수하는 비용을 드러내는 데 목적을 둔다.

---

## 1. 스레드 구성

```
                 ┌──────────────────────────────────────────────┐
   클라이언트 ──▶│  IOCP 워커 (4)                                │
                 │  완료 통보 수거 → 경계 복원 → 서비스 결정 → 적재│
                 │  ※ 상태 접근 · DB 호출 · 파일 I/O 금지         │
                 └───────┬──────────────────────────┬───────────┘
                         │ 이중 버퍼 큐             │
          ┌──────────────▼────────────┐  ┌──────────▼───────────┐
          │  게임 서비스 (1)           │  │  채팅 서비스 (1)      │
          │  세션 표 · DB 요청         │─▶│  접속자 목록          │
          │  Echo Save History ...    │  │  Chat · 브로드캐스트   │
          └───────┬───────────▲───────┘  └──────────────────────┘
                  │ 요청 큐   │ 응답 큐
          ┌───────▼───────────┴───────┐
          │  DB 워커 (N)               │
          │  커넥션 1개 · 준비된 구문    │
          │  ※ 세션 키 해시로 배정      │
          └───────────────────────────┘

   회수 스레드 (1)  만료 판정 · 미완료 0인 연결 회수
   기록 스레드 (1)  로그 파일 쓰기
```

**서비스는 자기 상태를 단독으로 소유한다.** 그래서 게임 상태에 잠금이 없다.
서비스 사이에는 표가 아니라 값이 오간다.

접속이 8에서 2,000으로 늘어도 **스레드 수는 구성값으로만 정해진다.**
연결 수와 스레드 수를 분리하는 것이 완료 통보 모델을 쓰는 이유다.

---

## 2. 계층별 결정

### 2-1. 완료 통보 수거 — `src/net/io_service.cpp`

워커 수는 `코어수 / 2`, 하한 2 · 상한 4다.
워커는 대기와 분기만 하고 실제 처리는 다른 스레드가 맡으므로 코어를 다 쓸 이유가 없다.

실패한 완료 통보도 루프를 벗어나지 않고 실패 표시만 붙여 각 경로로 넘긴다.
**작업 객체 회수 경로를 하나로 유지**하기 위해서다.

청취 소켓에는 `SO_EXCLUSIVEADDRUSE` 를 건다. **`SO_REUSEADDR` 이 아니다.**
Windows 의 `SO_REUSEADDR` 은 POSIX 와 뜻이 다르다 — 이미 그 주소를 쓰는 소켓이 있어도
`bind` 가 성공한다. 같은 포트로 인스턴스를 둘 띄우면 두 번째가 실패하지 않고
들어오는 접속이 둘로 갈린다. 포트를 이미 쓰고 있으면 뜨지 않는 편이 낫다.

동시 접속에는 상한이 있다(`max_connections`, 기본 8,192).
접속 하나가 수신 버퍼와 송신 누적분을 들고 있으므로 상한이 없으면 접속 수가 그대로 메모리 사용량이 된다.
판정과 등록은 **같은 잠금 안에서** 한다. 나누면 워커 여러 개가 동시에 통과해 상한을 넘긴다.
넘어선 접속은 응답 없이 곧바로 끊는다 — 자리가 없는 상황에서 응답을 만드는 것 자체가 비용이다.

### 2-1-1. 상한 체계

밖에서 늘릴 수 있는 자원에는 전부 상한을 둔다. **하나라도 빠지면 나머지가 무의미해진다** —
막힌 곳이 아니라 뚫린 곳으로 늘어나기 때문이다.

| 자원 | 상한 | 넘으면 |
|------|------|--------|
| 동시 접속 | `max_connections` (8,192) | 곧바로 끊는다 |
| 받는 프레임 본문 | `kMaxInboundBody` (1KB) | 경계가 깨졌다고 보고 끊는다 |
| 연결당 수신 버퍼 | `kMaxCapacity` (16KB) | 끊는다 |
| **연결당 송신 누적분** | `send_buffer_limit_kb` (256KB) | **끊는다** |
| 연결당 요청 속도 | `message_rate_limit` (기본 없음) | 오류 코드 30 |
| 서비스 수신 큐 | `inbound_queue_cap` (8,192) | `inbound_full_policy` 에 따라 거절 또는 역압 |
| DB 큐 | 워커당 4,096 | 오류 코드 30 |
| DB 요청 수명 | `request_timeout_ms` (3초) | 질의를 시작하지 않는다 |

**여러 겹일 때는 무엇이 먼저 걸리는지가 결과를 정한다.**
큐 정책을 재려고 큐 상한만 낮추면, 거절 응답이 송신 누적분을 밀어 올려
**송신 상한이 먼저 걸리고 연결이 끊긴다.** 그러면 큐 정책의 차이가 아니라 송신 상한을 잰 것이 된다.
한 상한을 시험할 때는 나머지를 넉넉히 두어야 한다.

#### 상한을 방향별로 나눈 이유

받는 크기와 보내는 크기가 다르다.

```
받는 최대   Echo · Save 요청 = 길이 2 + 본문 512        =   514바이트
보내는 최대 History 응답 = 100행 × (8 + 2 + 512 + 8)   ≈ 53,000바이트
```

100배 차이다. 하나의 상수로 묶으면 큰 쪽에 맞춰야 하고,
그러면 **받는 쪽 버퍼가 실제 필요보다 100배 커진다.**
수신 버퍼 상한은 곧 접속당 메모리이고 접속 상한과 곱해지므로, 그 차이가 그대로 서버 전체 최악값이 된다.

| 구분 | 상한 | 접속 8,192 기준 최악 |
|------|------|-------------------|
| 하나로 묶는다면 (64KB) | 수신 버퍼 128KB | 1GB |
| **방향을 나누면** (받기 1KB) | 수신 버퍼 16KB | **128MB** |

#### 송신 누적분에 상한이 필요한 이유

상대가 응답을 읽지 않으면 커널 송신 버퍼가 막히고 `WSASend` 가 완료되지 않는다.
그동안 만들어진 응답은 전부 누적 버퍼에 쌓인다. 받는 쪽에는 상한이 여러 겹인데
**보내는 쪽에는 하나도 없으면, 요청을 계속 보내며 응답만 읽지 않는 상대가 서버 메모리를 가져간다.**

넘어섰을 때 **오류로 답하지 않고 곧바로 끊는다.** 그 오류 응답도 같은 버퍼에 쌓이기 때문이다 —
늘어나는 것을 늘려서 막을 수는 없다.

### 2-2. 작업 수명 — `src/net/connection.h`

커널은 요청을 접수한 뒤 **나중에** 버퍼와 작업 객체에 접근한다.
따라서 완료 통보가 오기 전에 해제되면 안 된다.

```
소켓 종료와 객체 해제를 분리한다.
close() 는 소켓만 닫는다.
해제는 미완료 작업이 0이 된 뒤에만 이루어진다.
```

연결이 끊긴 뒤에도 발행된 요청은 완료 통보로 되돌아온다.
해제 조건을 **시간이 아니라 상태**(`pending == 0`)로 둔 이유가 이것이다.

### 2-3. 수신 버퍼 — `src/net/receive_buffer.cpp`

연속 메모리 한 덩어리에 누적하고, 읽기·쓰기 위치는 전진만 한다.
여유가 부족해지면 **가장 싼 수단부터** 시도한다.

| 단계 | 조건 | 처리 | 비용 |
|------|------|------|------|
| 1 | 소비분 회수로 4KB 확보 가능 | 앞으로 이동 | 복사 (잔량에 비례) |
| 2 | 부족 · 상한 미만 | 8KB 확장 후 이전 | 할당 1 + 복사 1 |
| 3 | 상한 16KB 도달 | 수신 거부 → 연결 종료 | — |

용량은 이 서버가 **받는** 프레임 크기에서 유도한다.
일반 요청은 `헤더 6 + 길이 2 + 본문 512 = 520바이트` 이고, 받는 최대 프레임은 `6 + 1KB` 다.
기본 용량은 일반 요청 열댓 건 분량, 상한은 그 두 배면 된다.

**보내는 프레임 상한(64KB)을 여기 쓰지 않는다.** 그 값을 기준으로 잡으면
받는 쪽 버퍼가 실제 필요보다 100배 커지고, 그것이 접속 수와 곱해진다(2-1-1 참조).

확장된 버퍼는 **데이터가 완전히 비었을 때만** 되돌린다.
잔량이 있을 때 줄이면 이동이 한 번 더 생기고, 큰 메시지가 이어지는 구간에서
확장과 축소가 번갈아 일어난다.

### 2-4. 메시지 경계 — `src/proto/frame.h`

헤더 6바이트 = 길이(4) + 메시지 ID(2). **길이 필드에 헤더를 포함하지 않는다.**
`보유량 >= 6 + body_size` 한 번으로 완성 여부가 판정되고, 매번 빼는 연산이 사라진다.
그 뺄셈이 빠지는 것이 경계 버그의 전형적인 원인이다.

완성분은 **버퍼 내부를 가리키는 포인터로 반환**한다. 복사가 없는 대신
다음 수신 전에 소비를 마쳐야 한다.

### 2-5. 큐 항목 — `src/app/inbound_event.h`

`FrameView::body` 는 수신 버퍼 내부를 가리키므로 서비스 스레드로 넘기려면 복사해야 한다.
요청 본문의 상한이 정해져 있어(512바이트) **항목을 고정 크기 배열로 두었다.**
메시지마다 힙 할당이 생기지 않는다.

큐에 넣을 때도 밖에서 만들어 넘기지 않고 **큐 안의 자리에 직접 채운다.**
이동 한 번이 배열 전체 복사가 되기 때문이다.

접속 · 종료 · 메시지를 **한 큐에 태그로** 묶는다. 큐를 나누면
"접속보다 첫 메시지가 먼저 처리되는" 순서 역전이 생긴다.

### 2-6. 로직 스레드 — `src/core/logic_thread.cpp`

깨우는 방식을 주기 대기가 아니라 **신호**로 둔다.
Windows 의 기본 타이머 분해능은 15.625ms 다. 주기 대기로 두면 `sleep_for(1ms)` 를 요청해도
그만큼 자므로 왕복 지연이 그 값에 묶인다. 조건 변수로 깨우면 대기 시간이 분해능과 무관해진다.

잠들기 전에 200µs 만 회전한다. 문맥 전환 왕복이 메시지 하나 처리보다 비싸므로,
요청이 곧 이어질 구간에서는 깨우기 비용을 그대로 지연으로 물게 된다.

**소속 검사를 Release 빌드에서도 살려 둔다.**
다른 스레드에서 상태를 만지는 사고는 증상이 간헐적이라
부하 시험 중에 잡히지 않으면 잡을 기회가 없다.

### 2-6-1. 서비스 분리 — `src/app/service.h` · `service_router.cpp`

**스레드를 기능으로 나눈다.** 같은 기능의 메시지는 어느 세션의 것이든 한 서비스로 모인다.

```
IOCP 워커 ──▶ 경계 복원 ──▶ 메시지 ID 로 서비스 결정 ──▶ 그 서비스 큐에 적재
                                    │
              ┌─────────────────────┴─────────────────────┐
              ▼                                           ▼
   게임 서비스 (스레드 1)                        채팅 서비스 (스레드 1)
   세션 표 · DB 요청                             접속자 목록
   Echo · Save · History · Counter · Ping        Chat
              └──── 세션 키 전달 ────▶
```

| 서비스 | 소유 상태 | 담당 메시지 |
|--------|----------|-----------|
| 게임 | 세션 표(`session_key` · 통계) · DB 요청 | `Echo` · `Save` · `History` · `Counter` · `Ping` |
| 채팅 | 접속자 목록(`conn_id` → 연결 참조 · 표시 이름) | `Chat` |

#### 왜 기능으로 나누는가

여러 세션이 한꺼번에 얽히는 기능이 있기 때문이다. 브로드캐스트 · 매칭 · 파티 전투가 그렇다.

| 나누는 기준 | 같은 스레드에 모이는 것 | 잠금 없이 되는 것 |
|------|---------------------|-----------------|
| **기능** | 같은 기능의 **모든 세션** | 브로드캐스트 · 매칭 |
| 연결 | 한 세션의 **모든 기능** | 세션 상태 갱신 |

연결로 나누면 브로드캐스트 한 번에 스레드 간 전달이 접속 수만큼 필요하다.
기능으로 나누면 접속자 목록이 한 스레드에 있으므로 반복문 하나로 끝난다.

#### 잠금이 없는 이유

서비스가 자기 상태를 **단독으로 소유한다.** 남의 표를 들여다보지 않는다.

채팅 서비스는 게임 서비스의 세션 표를 보지 않는다.
자기 목록에 연결 참조를 들고 있고, `Connection::send` 가 자체 잠금을 갖고 있어
어느 스레드가 불러도 안전하다. 그래서 게임 상태에는 잠금이 하나도 없다.

#### 라우팅 — `src/app/service_router.cpp`

메시지 ID → 서비스 표는 **기동 시 한 번 만들고 그 뒤로는 읽기만 한다.** 그래서 잠금이 없다.

| 항목 | 처리 |
|------|------|
| 담당 서비스가 있는 메시지 | 그 서비스 큐에 적재한다 |
| 어느 서비스도 맡지 않는 메시지 | 오류 코드 2 로 답한다. 큐에 넣을 곳이 없으므로 라우터가 직접 답한다 |
| 접속 · 종료 | **모든 서비스에 보낸다.** 서비스마다 자기 목록이 따로다 |

#### 서비스 간 전달

접속하면 게임 서비스가 세션 키를 발급하고, 그 값을 채팅 서비스에 넘긴다.
채팅 서비스는 그 값으로 자기 목록의 표시 이름을 채운다.

```cpp
void ServiceRouter::post_to(ServiceId target, ServiceMessage msg);
```

**표를 넘기지 않고 값만 넘긴다.** 받는 쪽이 그것으로 자기 상태를 갱신한다.
서비스가 상대를 직접 알면 붙일 때마다 서로를 참조해야 하므로 라우터를 거친다.

#### 두 큐가 섞이는 자리

전달 항목은 수신 큐와 **다른 큐**로 들어온다. 한 접속에 대해 두 큐가 이렇게 채워진다.

```
접속 통지   IOCP 워커  ──▶ 채팅 서비스 수신 큐        (T0)
세션 키     게임 서비스 ──▶ 채팅 서비스 전달 큐        (T1 > T0)
채팅 요청   IOCP 워커  ──▶ 채팅 서비스 수신 큐        (T2 > T1)
```

세션 키는 게임 서비스가 접속 통지를 **처리한 뒤** 넣으므로 항상 접속 통지보다 늦고,
채팅 요청은 클라이언트가 세션 키 응답을 받은 뒤에야 보내므로 세션 키보다 늦다.

**전달 큐를 먼저 비운다.** 그래야 "세션 정보보다 그 세션의 메시지가 먼저" 처리되지 않는다.
그 대신 세션 키가 접속 통지보다 앞설 수 있다 — 접속 통지는 아직 수신 큐에 있기 때문이다.

| 도착 순서 | 처리 |
|-----------|------|
| 접속 통지 → 세션 키 | 목록에 이미 있으므로 표시 이름을 채운다 |
| 세션 키 → 접속 통지 | **잠깐 맡아 둔다.** 접속 통지가 같은 회차의 수신 큐에 있으므로 곧바로 옮겨진다 |

접속 통지가 항상 먼저 적재된다는 것이 두 번째 줄의 근거다.
맡아 둔 항목은 그 회차 안에 반드시 소비되므로 쌓이지 않는다.

#### 레인 — 서비스 안에서 다시 나누기

```
lane_index = connection_id % lane_count
```

한 서비스를 그 안에서 다시 나눌 수 있다. **기본은 1** 이고 `game_lane_count` 로 올린다.
한 서비스가 병목이 됐을 때 판단할 일이다.

| 성질 | 내용 |
|------|------|
| 상태 공유 | **없다.** 레인마다 상태를 따로 둔다. 그래서 스레드가 늘어도 잠금이 없다 |
| 연결 내 순서 | 보존된다. 같은 연결은 항상 같은 레인으로 간다 |
| DB 응답 | `conn_id` 로 **요청을 낸 레인에** 돌려보낸다. 다른 레인은 그 세션을 모른다 |
| 통계 | 레인이 자기 값을 기록한다. 다른 레인의 값을 읽으면 스레드 경계를 넘는다 |

**채팅 서비스는 레인 1 로 고정한다.** 나누면 접속자 목록이 갈라져
브로드캐스트가 레인 간 전달이 되고, 이 서비스를 둔 이유가 사라진다.

#### 예외 격리

처리 중 예외가 서비스 스레드를 벗어나면 그 스레드가 끝나고 프로세스가 함께 내려간다.
그래서 **격리 단위를 항목 하나로 둔다.**

```
항목 하나를 감싼다 → 예외가 나온 연결만 끊는다 → 나머지 항목은 그대로 처리한다
```

배치를 통째로 감싸면 예외 하나에 뒤따르던 항목이 함께 버려진다.
터진 세션은 상태가 어디까지 반영됐는지 알 수 없으므로 표에서 지운다.
남겨 두면 다음 메시지가 같은 자리에서 다시 튕긴다. 발생 건수는 `faults` 로 기록한다.

#### 수신 큐 상한

서비스 큐에도 상한을 둔다(`inbound_queue_cap`, 기본 8,192).
소비가 밀리는 동안에도 IOCP 워커의 적재는 계속되므로, 상한이 없으면 그 차이가 그대로 메모리 증가가 된다.

| 항목 | 상한 적용 | 이유 |
|------|----------|------|
| 메시지 | **적용** | 아래 두 정책 중 하나로 처리한다 |
| 접속 · 종료 | 적용하지 않는다 | 막으면 세션이 표에 남아 회수되지 않는다 |

#### 가득 찼을 때 — 거절과 역압

`inbound_full_policy` 로 고른다. **어느 쪽이든 메시지를 잃지 않는다.** 다른 것은 누가 기다리느냐다.

| | `reject` (기본) | `backpressure` |
|---|---|---|
| 그 메시지 | 오류 코드 30 으로 답한다 | **수신 버퍼에 남긴다** |
| 그 연결 | 계속 받는다 | 다음 수신을 걸지 않는다 |
| 상대 | 거절을 받고 스스로 판단한다 | TCP 창이 줄어 송신이 저절로 막힌다 |
| 재개 | — | 서비스 스레드가 큐를 비운 뒤 다시 걸어 준다 |

**역압에서 프레임을 버리지 않는 것이 핵심이다.**
큐에 못 넣었다고 그 프레임을 버리면 기다리는 쪽은 오지 않을 응답을 기다린다.
그래서 메시지 처리기가 "지금은 받을 수 없다" 를 돌려줄 수 있게 하고,
그 경우 수신 버퍼의 소비 위치를 옮기지 않는다. 다시 걸릴 때 같은 자리에서 이어 읽는다.

```
IOCP 워커  큐가 가득 → 프레임을 남긴다 → 수신을 멈춘다 → 연결을 보류 목록에 넣는다
서비스 스레드 큐를 비운다 → 보류 목록을 비우며 재개를 통지한다
IOCP 워커  통지를 받아 남은 프레임부터 소비하고 다시 수신을 건다
```

재개도 완료 포트를 거친다. 서비스 스레드가 `WSARecv` 를 직접 부르지 않는 이유는 송신과 같다.

> 다시 거는 순간 또 가득 찰 수 있다. 그러면 그 안에서 다시 멈춘다.
> 오르내림이 생기지만 그것이 속도를 맞추는 과정이다.

### 2-7. 송신 — `src/net/connection.cpp`

서비스 스레드는 **보낼 것을 누적하기만 하고 발행은 IOCP 워커에게 맡긴다.**
`PostQueuedCompletionStatus` 로 통지만 남긴다.

통지도 시스템 호출이므로, 쌓인 것이 없으면 메시지 하나에 호출이 두 번 드는 셈이다.
그래서 `send_mode = direct` 로 보내는 쪽이 바로 발행하는 경로도 함께 둔다.
**두 경로의 처리량 차이는 관측되지 않았다**(`docs/benchmark.md` 1-3).
기본을 `notify` 로 두는 근거는 그것이 더 빨라서가 아니라,
서비스 스레드가 병목이 되는 조건에서 발행 비용을 워커로 넘길 수 있기 때문이다.

발행 한 번에 몇 건이 실려 나가는지는 `echo_send_messages_total / echo_send_issues_total` 로 본다.

`WSASend` 를 서비스 스레드에서 부르면 그 시스템 호출 비용이 그대로
단일 스레드의 처리량 상한이 된다. 발행을 워커로 넘기면 그 상한이 사라진다.
서비스 스레드의 메시지당 처리 시간은 **1µs 미만**이다.

대기분은 버퍼 하나에 이어 붙이고, 발행할 때는 두 버퍼를 **맞바꾸기만** 한다.
연결당 발행이 항상 한 건이므로 전송 순서가 뒤바뀌지 않는다.

#### 전량이 나가지 못했을 때

중첩 송신은 대체로 요청한 전량을 보내고 완료된다. 그러나 보장은 아니다.
전량이 아니라고 연결을 끊으면 **보내던 데이터를 잃는다.**

```
보낸 만큼만 잘라 낸다 → 남은 구간을 누적분 맨 앞에 되돌린다 → 다시 발행한다
```

남은 구간이 **발행 중에 쌓인 것보다 앞에** 서야 순서가 보존된다.
앞에 끼워 넣는 비용이 들지만 이 경로는 드물고, 흔한 경로(전량 전송)에는 아무것도 더하지 않는다.
한 바이트도 나가지 못한 경우는 되돌려도 같은 자리에서 멈추므로 연결을 끊는다.

발생 횟수는 `echo_partial_sends_total` 로 노출한다.
드물어서 부하 시험으로는 잡히지 않는 경로이므로, 되돌리는 계산만 떼어 내
단위 테스트로 고정해 두었다(`tests/test_send_requeue.cpp`).

### 2-8. DB 워커 — `src/db/db_worker_pool.cpp`

같은 세션 키의 요청이 서로 앞지르지 않아야 한다. 그 방법이 두 가지 있고,
`dispatch` 설정으로 고른다. **어느 쪽이든 순서는 보장된다. 다른 것은 배정 방법이다.**

#### static — 해시로 워커를 고정한다

```
worker_index = hash(session_key) % worker_count
```

같은 키는 항상 같은 워커로 간다. 그래서 **순서가 배정 규칙에서 그냥 따라 나온다.**
처리 중인 키 집합도, 배정 잠금도 필요 없다.

> 비용: 분산이 정적이다. 키가 워커 수에 비해 적으면 **해시가 겹쳐 노는 워커가 생긴다.**

#### dynamic — 처리 중인 키를 피해 배정한다 — `src/db/request_dispatcher.cpp`

키를 워커에 미리 묶지 않는다. 대신 "지금 처리 중인 키"를 표시해 두고
그 키의 다음 요청은 앞선 처리가 끝날 때까지 내보내지 않는다.

```
push(req)          키별 줄에 넣는다. 처리 중이 아니면 내보낼 목록에 올린다
take()   → req     내보낼 목록에서 하나 꺼내고 그 키를 처리 중으로 표시한다
finish(key)        표시를 지운다. 밀려 있던 같은 키가 있으면 다시 올린다
```

키마다 줄을 따로 둔다. 목록 하나를 훑는 방식이면 처리 중인 키가 앞을 막을 때
그만큼 훑는 길이가 늘어난다. 키별로 나누면 그 비용이 없다.

> 비용: 배정마다 잠금을 잡고, 키별 상태를 유지해야 한다.

#### 어느 쪽을 쓰나

| 조건 | 유리한 쪽 |
|------|----------|
| 키 수가 워커 수에 비해 적다 | **dynamic.** static 은 해시가 겹쳐 워커가 논다 |
| 키마다 부하가 다르다 | **dynamic.** 느린 키가 같은 워커의 다른 키를 막지 않는다 |
| 키 수가 워커 수보다 훨씬 많고 부하가 고르다 | **static.** 배정 비용이 아예 없다 |

키 N개를 워커 4개에 무작위로 나눌 때 **모든 워커가 최소 하나를 받을 확률**은
N=4 에서 9.4%, N=8 에서 62.3%, N=16 에서 96% 다.
즉 키가 적을 때 static 이 워커를 놀리는 것은 우연이 아니라 구조다.
측정값은 `docs/benchmark.md` 3절에 있다.

두 방식 모두 큐 상한을 넘으면 **거절한다.** 무한히 쌓느니 거절하는 편이 낫다.
상한 총량은 양쪽이 같다(워커당 4,096 × 워커 수). 총량이 다르면 나란히 잴 수 없다.

### 2-8-1. 배치 커밋 — `src/db/db_worker_pool.cpp`

`Save` 하나에 드는 시간의 대부분은 질의가 아니라 **커밋**이다.

```
질의(INSERT) 자체     수십 µs
커밋 한 번            8~9ms      ← 전체의 96%
```

가장 엄격한 지속성 설정에서는 커밋마다 디스크 동기화가 두 번 일어난다(2절).
워커를 늘리면 동시에 도는 커밋이 늘어날 뿐, **커밋 하나의 값은 그대로다.**

연달아 나오는 `Save` 를 한 트랜잭션으로 묶으면 그 비용을 안에 든 요청들이 나눠 갖는다.

```
begin_batch()
  INSERT × N          ← 각각 수십 µs
commit_batch()        ← 8~9ms 를 N 건이 나눈다
```

#### 기다렸다 모으지 않는다

배치를 채우려고 대기하지 않는다. **지금 큐에 있는 것만 묶는다.**

| 상황 | 배치 크기 | 결과 |
|------|----------|------|
| 한가하다 | 1 | 묶을 것이 없으니 평소 경로로 간다. 지연이 늘지 않는다 |
| 밀린다 | 상한까지 | 밀린 만큼 묶이고, 그만큼 빨리 빠진다 |

부하에 따라 저절로 맞춰진다. 기다렸다 모으는 방식은 한가할 때 지연을 그냥 늘린다.

#### 묶지 않는 것

| 종류 | 이유 |
|------|------|
| `Counter` | 자체 트랜잭션을 연다. 겹쳐 열 수 없다 |
| `History` | 읽기라 커밋이 없다. 묶어도 얻을 것이 없다 |
| 기한을 넘긴 요청 | 실행하지 않아야 한다. 묶으면 그 판정이 커밋 뒤로 밀린다 |

`Save` 가 아닌 요청을 만나면 **모아 둔 것을 먼저 커밋한다.**
같은 키의 `Save` 가 아직 커밋되지 않았는데 `History` 를 실행하면
그 결과에 방금 저장한 것이 빠지기 때문이다.

#### 감수하는 비용

**하나가 실패하면 그 트랜잭션 전체가 되돌아간다.** 같은 배치에 든 다른 요청도 함께 실패한다.
이것이 "묶는다" 는 말의 뜻이고, 배치 크기를 키울수록 한 번의 실패가 미치는 범위도 커진다.

측정값은 `docs/benchmark.md` 2절에 있다 — 배치 128 에서 처리량 **4.8배**, p50 **5배** 감소.
그리고 **DB 커넥션 6개를 배치 하나로 대신할 수 있다.**

### 2-9. 재연결 — `src/db/mysql_connection.cpp`

**자동 재연결(`MYSQL_OPT_RECONNECT`)을 쓰지 않는다.**
자동 재연결은 세션 상태를 조용히 버리고 **준비된 구문을 전부 무효화**한다.
끊김을 직접 감지해 다시 연결하고 구문을 다시 준비한다.

감지 경로가 두 개다.

| 경로 | 시점 | 목적 |
|------|------|------|
| 질의 실패 | `CR_SERVER_GONE_ERROR(2006)` · `CR_SERVER_LOST(2013)` | 사용 중 끊김 |
| 유휴 감시 | `mysql_ping`, 3초 주기 | **쓰지 않는 동안의 끊김** |

유휴 감시가 없으면 끊긴 뒤 **첫 요청 한 건이 사용자 오류로 나간다.**

재시도는 **안전한 요청에만** 한 번 허용한다.

| 요청 | 재시도 | 이유 |
|------|--------|------|
| `History` | O | 읽기라 몇 번을 해도 같다 |
| `Counter` | O | 멱등성 키가 있어 두 번 반영되지 않는다 |
| `Save` | **X** | 앞선 시도가 커밋됐는지 알 수 없다 |

### 2-10. 두 가지 DB 접근 경로 — `sql/002_procedures.sql`

같은 일을 하는 경로를 둘 다 둔다. 설정(`use_procedures`)으로 고른다.

| | 직접 SQL | 저장 프로시저 |
|---|---------|-------------|
| 구문 | 준비된 구문 5종 | `CALL` 3종 |
| `Counter` 왕복 | **5회** | **1회** |
| 트랜잭션 | 애플리케이션이 연다 | 프로시저 안에 있다 |
| 판정 위치 | 애플리케이션 | DB |

측정 결과는 `docs/benchmark.md` §2-2 에 있다. 요약하면
**왕복이 많은 트랜잭션에서만 이득이고(4%), 단일 질의에서는 손해(24%)** 다.
커밋 지속성 비용이 지배적인 환경에서 왕복 최적화의 효과는 제한적이다.

프로시저를 남겨 둔 이유는 속도가 아니라 **판정을 한 덩어리로 묶는 것**이다.
`sp_apply_counter` 는 트랜잭션 · 멱등성 판정 · 값 조회를 한 번의 호출 안에 둔다.
애플리케이션이 중간에 죽어도 절반만 반영된 상태가 생기지 않는다.

`CALL` 은 결과셋을 여러 개 돌려준다. 프로시저가 만든 것 뒤에 종료 상태가 하나 더 붙는다.
비워 두지 않으면 다음 질의가 "명령 순서 오류" 로 실패하므로
`drain_extra_results()` 로 반드시 비운다.

### 2-11. 멱등성 — `sql/001_schema.sql`

`Counter` 는 클라이언트가 만든 `request_key` 를 기본 키로 선점한다.

```
START TRANSACTION
  INSERT INTO counter_request(request_key, session_key)     ← 중복이면 여기서 실패
  INSERT INTO echo_counter(...) ON DUPLICATE KEY UPDATE ...
COMMIT
```

중복 키 오류는 **실패가 아니라 "이미 반영됨" 판정**이다.
되돌린 뒤 현재 값을 읽어 `already_applied = 1` 과 함께 돌려준다.

> 응답을 받지 못한 클라이언트가 재시도하는 것은 옳다.
> 서버는 그 재시도에 같은 결과를 돌려주어야 한다.
> 재전송을 오류로 응답하면 정상적인 재시도가 실패로 보인다.

방어가 세 겹이다.

| 층 | 위치 | 수단 |
|----|------|------|
| 1 | 서버 | 세션 키 단위 직렬화 — 같은 세션의 동시 진입이 없다 |
| 2 | DB | `PRIMARY KEY(request_key)` — 최종 판정 |
| 3 | DB | `version` 컬럼 — 낙관적 동시성 제어 |

### 2-11-1. 지연 분포 — `src/core/latency.cpp`

평균만으로는 "가끔 튀는 요청" 을 볼 수 없다. 실측이 그 차이를 보여준다.

```
로직 처리 시간   평균 0.6~0.8µs   p99 4.4µs   최댓값 107µs
```

**평균과 최댓값이 100배 넘게 벌어진다.** 평균만 보면 이 서버는 항상 1µs 안에 답하는 것처럼 보인다.

표본을 모두 들고 있으면 요청 수에 비례해 메모리가 는다.
구간별 개수만 세면 요청이 몇 건이든 크기가 고정된다(551칸 · 4.4KB).
대신 값이 구간 폭만큼 뭉개진다 — 백분위를 보는 목적에는 그 정도면 된다.

구간은 아래로 갈수록 넓다. 짧은 쪽을 촘촘히 보는 편이 쓸모 있고,
긴 쪽은 "몇 밀리초대인가" 만 알면 되기 때문이다.

| 범위 | 구간 폭 | 칸 수 |
|------|--------|------|
| 0 ~ 99µs | 1µs | 100 |
| 100µs ~ 1ms | 10µs | 90 |
| 1ms ~ 10ms | 100µs | 90 |
| 10ms ~ 100ms | 1ms | 90 |
| 100ms ~ 1s | 10ms | 90 |
| 1s ~ 10s | 100ms | 90 |
| 10s 이상 | 한 칸에 모은다 | 1 |

처리 시간만 나노초로 잰다. 마이크로초 단위로는 대부분이 0 이 되어 분포가 만들어지지 않는다.

> 재는 행위 자체가 값에 섞인다. 항목마다 끝난 시각을 다음 항목의 시작으로 써서
> 시계 호출을 한 번으로 줄였지만, 그 한 번은 여전히 측정값 안에 있다.
> A/B 로 비교했을 때 처리량 차이는 관측되지 않았다.

### 2-11-2. 요청 속도 제한 — `src/net/rate_limiter.h`

한 연결이 서버를 독점하지 못하게 한다. 초당 채우는 몫과 모아 둘 수 있는 몫을 나눈다.

```
초당 rate 개씩 채운다. 최대 burst 개까지 모인다.
메시지 하나가 한 개를 쓴다. 남은 것이 없으면 그 메시지를 거절한다.
```

평균만 보면 짧은 폭주를 막지 못하고, 순간값만 보면 정상 사용을 막는다. 두 값을 따로 두는 이유다.

**판정은 큐에 넣기 전에 한다.** 적재한 뒤에 걸러 내면 폭주 연결의 메시지가 이미 큐를 차지한 뒤다.
연결마다 하나씩 두고 그 연결의 수신 경로에서만 만지므로 잠금이 없다.

기본값은 제한 없음이다. 부하 측정은 한 연결이 낼 수 있는 최대치를 재는 것이라
제한이 켜져 있으면 그 값을 잴 수 없다.

### 2-11-3. DB 요청 기한 — `src/db/db_worker_pool.cpp`

요청마다 마감을 둔다. 기한은 **큐에 넣는 시점부터** 센다 — 워커 앞에서 기다린 시간도 함께 들어간다.

워커는 요청을 꺼낸 뒤 기한을 먼저 본다. 넘겼으면 질의를 시작하지 않고 오류로 답한다.

```
이미 늦은 질의를 실행해도 기다리던 쪽은 대개 받지 않는다.
그 시간에 워커를 쓰면 뒤에 밀린 요청까지 함께 늦는다.
```

실행 중인 질의를 중간에 끊지는 않는다. 판정은 **시작 시점에만** 한다.
도는 질의를 죽이려면 별도 세션에서 개입해야 하고, 그쪽이 더 위험하다.

효과는 `docs/benchmark.md` 6절에 있다 — 만료 1.4% 로 p50 이 101ms 에서 8ms 가 된다.

### 2-12. 기록과 회전 — `src/core/log.cpp`

문자열 조립은 호출 스레드에서 끝내고 큐에는 완성된 줄만 싣는다.
파일 쓰기는 기록 스레드가 맡는다. 서비스 스레드가 파일 I/O 로 멈추면 그 순간 모든 처리가 함께 멈춘다.

회전 판정도 기록 스레드가 단독으로 한다. 그래서 회전에 잠금이 없다.

| 판정 | 기준 |
|------|------|
| 크기 | 쓴 양이 `max_mb` 를 넘었을 때. 파일 크기를 매번 물으면 그만큼 시스템 호출이 는다 |
| 날짜 | 파일을 연 날짜가 바뀌었을 때 |

넘길 때는 `logs/server.YYYYMMDD-HHMMSS.log` 로 이름을 바꾸고 새 파일을 연다.
같은 초에 두 번 넘기면 뒤에 번호를 붙인다. 보관 개수(`keep_files`)를 넘긴 것부터 지운다.

넘기지 못했더라도 파일은 다시 연다. 로그를 못 넘긴 것 때문에 기록 자체를 멈추지는 않는다.

### 2-12-1. 관리 포트 — `src/net/admin_server.cpp`

감시 도구와 로드밸런서가 볼 지점을 하나 둔다.

| 경로 | 응답 |
|------|------|
| `GET /health` | 200 `ok` · 503 `unavailable` |
| `GET /metrics` | 200 노출 형식 텍스트 |

**주 경로와 완전히 분리한다.** 완료 포트를 쓰지 않고 스레드 하나로 차단 처리한다.
이 포트에 오는 것은 몇 초에 한 번의 수집 요청뿐이라
지연보다 "관리 요청이 게임 처리에 섞이지 않는다" 는 쪽이 중요하다.

HTTP 로 답하는 이유는 붙일 수 있는 것이 많아서다. 수집 도구 · 로드밸런서 · `curl` 이 그대로 붙는다.

#### 정상 아님으로 답하는 조건

| 조건 | 이유 |
|------|------|
| 종료 신호를 받은 뒤 | 드레인이 도는 동안 새 트래픽을 받지 않는 편이 낫다. 로드밸런서가 미리 빼 준다 |
| DB 워커가 하나도 붙지 못한 상태 | DB 를 쓰는 요청은 전부 실패한다 |

관리 포트는 **드레인이 끝날 때까지 살려 둔다.** 먼저 닫으면 빠지라는 신호를 줄 수단이 없어진다.

#### 지표

로그는 사람이 읽는 것이고 지표는 수집 도구가 읽는 것이다.
5초마다 한 줄씩 남기는 로그로는 추세도 경보도 만들 수 없다.

레인 통계는 그 레인의 스레드 소유라 관리 스레드가 직접 읽을 수 없다.
**통계 주기마다 레인이 사본을 남기고, 읽는 쪽은 그 사본만 본다.**

백분위는 계산해서 내보낸다. 원시 표본은 크기가 감당되지 않고, 받는 쪽에서 다시 분포를 만들어야 한다.

**사본에 담는 것은 백분위가 아니라 분포 자체다.**
서로 다른 분포의 백분위는 더하거나 평균 낼 수 없다. 그러나 분포는 합칠 수 있다 —
구간이 고정이므로 칸별로 더하면 합쳐진 분포가 그대로 나온다.

```
레인마다 분포 사본 → 칸별로 더한다 → 합쳐진 분포에서 백분위를 한 번 계산한다
```

**서비스끼리는 합치지 않는다.** "항목 하나" 가 뜻하는 일이 다르기 때문이다 —
게임의 한 건은 메시지 하나이고, 채팅의 한 건은 접속자 전원에게 보내는 일이다.
그래서 분포 지표에는 `service` 라벨이 붙는다.

```
echo_process_nanoseconds{service="game",quantile="0.99"} 6600
echo_broadcast_microseconds{service="chat",quantile="0.99"} 2400
```

브로드캐스트와 서비스 간 전달도 지표로 나간다.
채팅 1건이 실제 송신 몇 번이 됐는지는 `echo_broadcasts_total` 과
`echo_broadcast_sends_total` 의 비로 읽는다.

표본 수를 함께 내보낸다. 백분위는 마지막 기록 주기의 값이라
그 주기에 트래픽이 없으면 0 이 되는데, 이 값이 없으면
"빨랐던 것" 과 "잴 것이 없던 것" 을 구분할 수 없다.

### 2-13. 정상 종료 — `src/main.cpp`

받아 둔 일을 마치고 내려간다. **순서가 곧 설계다.**

```
1. 수락 중단        새 접속을 먼저 막는다. 그래야 남은 일이 늘지 않는다
2. DB 드레인        새 요청만 거절하고, 큐에 남은 질의는 기한까지 정상 처리한다
3. 서비스 드레인     서비스가 그 응답을 소비해 송신에 싣는다
4. 송신 드레인      누적분이 실제로 소켓으로 나갈 때까지 기다린다
5. 종료             연결을 닫고 워커와 스레드를 정리한다
```

연결을 먼저 닫으면 응답을 만들어도 받을 상대가 남아 있지 않다.
각 단계는 `shutdown_drain_ms` 를 상한으로 두고, 넘기면 남은 요청에 `Unavailable` 로 답한 뒤 내려간다.
**기다리는 데도 상한이 필요하다.** 상한이 없으면 종료가 끝나지 않는 경우가 생긴다.

## 3. 감수한 비용

| 배치 커밋 | 커밋 비용을 여러 건이 나눠 갖는다. 커넥션을 대신할 수 있다 | 하나가 실패하면 그 배치 전체가 되돌아간다 |
| 역압 | 거절 없이 속도를 맞춘다 | 상대의 왕복이 길어진다. 보류 목록과 재개 통지가 필요하다 |

| 고정 크기 큐 항목 | 힙 할당 0 | 항목당 640바이트 |
| 항목 단위 예외 격리 | 예외 하나가 프로세스를 내리지 않는다 | 터진 연결은 상태를 알 수 없어 끊어야 한다 |
| 큐 · 접속 상한 | 밀리는 동안에도 메모리가 늘지 않는다 | 상한에 닿으면 거절이 생긴다 |
| 상한을 방향별로 분리 | 받는 쪽 버퍼가 실제 크기에 맞는다 | 상수가 둘로 늘고 어느 쪽인지 따져야 한다 |
| 송신 상한 초과 시 절단 | 한 연결이 메모리를 가져가지 못한다 | 느린 상대가 정상이어도 끊긴다 |
| 구간 히스토그램 | 표본 수와 무관하게 크기가 고정된다. 칸이 같아 레인끼리 합칠 수 있다 | 값이 구간 폭만큼 뭉개진다 |
| 항목마다 시각 측정 | 백분위를 볼 수 있다 | 재는 비용이 측정값에 섞인다 |
| DB 요청 기한 | 늦은 요청을 버려 나머지 지연을 지킨다 | 버린 요청은 실패로 끝난다 |
| 관리 포트 전용 스레드 | 관리 요청이 주 경로에 섞이지 않는다 | 스레드 하나와 포트 하나를 더 쓴다 |
| 자동 재연결 미사용 | 구문 무효화를 피한다 | 감지 · 재준비를 직접 해야 한다 |
| `Save` 재시도 안 함 | 행이 중복되지 않는다 | 끊김 시 사용자가 다시 보내야 한다 |
| 완료 통보 모델 | 스레드가 연결 수와 무관 | Windows 전용이다 |

## 4. 다른 플랫폼으로 옮긴다면

교체 대상은 **통보 수거 계층 하나**다.

| 그대로 | 교체 |
|--------|------|
| `ReceiveBuffer` · 프레임 · 큐 · 서비스 스레드 · DB 계층 | `IoService` · `Connection` 의 발행 부분 |

완료 통보(proactor)를 준비 통보(reactor)로 바꾸면
"준비됐다" 를 받은 뒤 직접 읽고 쓰는 형태가 된다.
작업 객체 수명 규칙은 오히려 단순해진다 — 커널이 나중에 버퍼를 건드리지 않기 때문이다.
