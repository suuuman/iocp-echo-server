# iocp-echo-server

Windows IOCP 기반 비동기 TCP 서버. 에코 왕복이라는 최소 도메인 위에
**네트워크 · 비동기 · DB** 세 계층을 얹은 참조 구현이다.

기능을 늘리는 대신 **계층의 경계와 그 경계에서 감수하는 비용**을 드러내는 데 목적을 둔다.

```
                            ┌──▶ 게임 서비스 ──▶ DB 워커 풀
클라이언트 ──▶ IOCP 워커 ──┤         │  ▲             │
              메시지 ID 로  │         │  └── 응답 큐 ◀─┘
              서비스 결정   │         └── 세션 키 전달 ─┐
                            └──▶ 채팅 서비스 ◀──────────┘
                                     └─▶ 접속자 전원에게 브로드캐스트
```

**스레드를 기능으로 나눈다.** 같은 기능의 메시지는 어느 세션의 것이든 한 서비스로 모이므로,
브로드캐스트처럼 여러 세션이 얽히는 일이 그 스레드 안에서 끝난다.

서비스는 자기 상태를 단독으로 소유한다. 남의 표를 보지 않고 값만 주고받는다.
그래서 **게임 상태에 잠금이 하나도 없다.**

접속 **8 → 2,000** 으로 250배가 되어도 서버 스레드 수는 **구성값으로만 정해진다.**
메모리는 접속당 약 10KB 씩만 는다 — 2,000 접속에서 40MB 안쪽이다.

같은 일을 하는 경로가 둘 있는 자리에서는 **양쪽을 다 구현하고 측정으로 비교한다.**
직접 SQL ↔ 저장 프로시저, 해시 고정 배정 ↔ 동적 배정, 건별 커밋 ↔ 배치 커밋이 그렇다.

## 무엇을 보여주는가

| 계층 | 내용 |
|------|------|
| 네트워크 | 완료 포트, `AcceptEx` · `ConnectEx` 사전 게시, 길이 프리픽스 경계 복원, 송신 병합 |
| 비동기 | 이중 버퍼 큐, **기능 축 서비스 분리**, 서비스 간 전달, 브로드캐스트, 세션 키 단위 직렬화, 하트비트 |
| DB | MySQL C API, 준비된 구문, **저장 프로시저**, 트랜잭션, 멱등성 키, 유휴 감시와 재연결 |
| 비교 | 같은 일을 하는 경로를 **둘 다 구현하고 측정한다** — 직접 SQL ↔ 프로시저, 해시 고정 ↔ 동적 배정, 건별 ↔ 배치 커밋 |
| 자료구조 | 스트림 버퍼의 재정렬 · 확장 · 축소 3단 정책, 고정 크기 큐 항목 |
| 운영 | 항목 단위 예외 격리, **밖에서 늘릴 수 있는 자원에 전부 상한**(접속 · 프레임 · 수신 버퍼 · 송신 누적 · 큐 · 속도 · DB 기한), 로그 회전, 드레인 종료 |
| 관측 | 지연 분포(p50 · p95 · p99), 헬스 체크와 지표 노출을 위한 관리 포트 |

구조와 근거는 [`docs/architecture.md`](docs/architecture.md) 에 있다.

## 측정 결과

Intel i7-12700F / Windows 11 / MSVC Release / 서버와 봇 같은 장비 / 본문 64바이트

### `Echo` — DB 미접촉

| 동시 접속 | 처리량 | p50 | p99 | 서버 스레드 | 서버 메모리 |
|-----------|--------|-----|-----|------------|------------|
| 8 | 220,008 msg/s | 34µs | 65µs | 18 | 21.1MB |
| 256 | 251,460 msg/s | 1,003µs | 1,272µs | 18 | 23.6MB |
| 2,000 | 195,996 msg/s | 9,954µs | 14,274µs | 18 | 40.0MB |

### 브로드캐스트 — 요청 하나가 접속 수만큼의 송신

말하는 접속 1개가 10ms 간격으로 보내고 나머지는 받기만 한다.

| 동시 접속 | 확산 | 처리량 | 왕복 p50 | 왕복 p99 | 서버 p50 |
|-----------|------|--------|---------|---------|---------|
| 64 | 64.0 | 4,083 push/s | 270µs | 736µs | 91µs |
| 256 | 256.0 | 16,397 push/s | 564µs | 1,154µs | 170µs |
| 1,000 | 1,000.0 | 63,920 push/s | 1,836µs | 3,774µs | 450µs |

**확산은 접속 수와 정확히 같다.** 접속자 목록이 한 스레드에 있으므로 반복문 하나로 끝난다.
서비스 간 전달(게임 → 채팅)은 p50 **1~2µs** 다.

### 기능 축 — 채팅이 게임 처리를 막는가

`Echo` 256 접속에 채팅 256 접속을 함께 붙였다.

| 조건 | `Echo` 처리량 | 게임 처리 시간 |
|------|-------------|--------------|
| 채팅 없음 | 254,991 msg/s | **0.58µs/메시지** |
| 채팅 256 동시 (13만 push/s) | 210,934 msg/s | **0.60µs/메시지** |

**메시지당 처리 시간이 사실상 그대로다.** 서버가 내보낸 메시지는 25.5만에서 34.2만 건으로
34% 늘었는데 게임 쪽 손실은 17% 다. 두 서비스가 각자의 상태만 만지기 때문이다.

### 평균이 감추는 것

같은 구간을 평균과 분포로 나란히 본 값이다.

| 구간 | 평균 | p50 | p99 | 최댓값 |
|------|------|-----|-----|-------|
| 게임 처리 | 0.8µs | 610ns | **4.4µs** | **107µs** |
| DB 질의 | 8.5ms | 8.2ms | 19ms | — |
| DB 왕복 | — | 27ms | 55ms | 70ms |

**평균만 보면 이 서버는 항상 1µs 안에 답하는 것처럼 보인다.** 최댓값은 그 130배다.
DB 도 마찬가지다 — 질의는 8.2ms 인데 왕복은 27ms 이고, 그 차이가 워커 앞에서 기다린 시간이다.

### DB 요청 기한 — 늦은 요청을 버리면 나머지가 빨라진다

`Save` 48 접속 · DB 워커 4.

| 기한 | 처리량 | p50 | p99 | 만료 |
|------|--------|-----|-----|------|
| 없음 | 475 msg/s | 101,239µs | 157,733µs | 0 |
| 20ms | 455 msg/s | **8,056µs** | **26,843µs** | 1.4% |

**요청의 1.4% 를 버리고 p50 을 12배 줄였다.** 처리량은 거의 그대로다.
기한을 넘긴 요청이 질의를 시작하지 않으면 워커가 빨리 다음으로 넘어가고, 줄이 짧아진다.

### DB 왕복 (64 접속)

| DB 워커 | `Save` 처리량 | `Save` p50 |
|---------|--------------|-----------|
| 4 | 475 msg/s | 136,881µs |
| 24 | 2,366 msg/s | 23,358µs |

### 워커 배정 — 해시 고정 대 처리 중인 키 회피

같은 세션 키의 순서는 어느 쪽이든 보장된다. 갈리는 것은 배정이 고른가다.
`Save` 부하 · DB 워커 4 기준.

| 접속 | 방식 | 처리량 | p99 | 워커별 처리 건수 |
|------|------|--------|-----|-----------------|
| 4 | `static` | 356 msg/s | 24,357µs | **0** / 972 / 957 / 954 |
| 4 | `dynamic` | **481 msg/s** | **15,581µs** | 972 / 973 / 970 / 971 |
| 64 | `static` | 482 msg/s | 240,050µs | 991 / 986 / 998 / 977 |
| 64 | `dynamic` | 500 msg/s | **156,949µs** | 1026 / 1023 / 1029 / 1026 |

키 4개를 워커 4개에 무작위로 나눌 때 모든 워커가 하나씩 받을 확률은 **9.4%** 다.
해시 고정이 워커를 놀리는 것은 우연이 아니라 구조이고, 접속 4 반복 측정 3회에서 모두 재현됐다.

**처리량은 대부분 구간에서 비슷하다. 갈리는 것은 꼬리 지연이다.**
`dynamic` 은 대기를 고르게 펴서 중앙값은 올라가고 p99 는 내려간다.

### 수신 큐가 가득 찰 때 — 거절과 역압

어느 쪽이든 메시지를 잃지 않는다. 다른 것은 누가 기다리느냐다.
큐 상한 64 · 응답을 기다리지 않고 밀어넣는 클라이언트.

| 연결 | 정책 | 보낸 요청 | 정상 응답 | 거절 |
|------|------|----------|----------|------|
| 16 | `reject` | 5,705,089 | 5,702,748 | 2,341 |
| 16 | `backpressure` | 5,903,671 | **5,903,671** | **0** |
| 128 | `reject` | 1,210,171 | 1,207,595 | 2,576 |
| 128 | `backpressure` | 1,214,402 | **1,214,402** | **0** |

**역압에서는 보낸 수와 응답 수가 정확히 같다.** 다음 수신을 걸지 않으면 TCP 창이 줄어
상대의 송신이 저절로 막히기 때문이다. 그동안 프레임은 수신 버퍼에 남는다 —
**버리면 기다리는 쪽이 오지 않을 응답을 기다린다.**

### 배치 커밋 — 커밋 하나를 여러 건이 나눠 갖는다

`Save` 한 건에 드는 시간의 96%가 커밋이다. 연달아 오는 것을 한 트랜잭션으로 묶었다.

| 배치 | 처리량 | p50 | 배치 1 대비 |
|------|--------|-----|-----------|
| 1 | 480 msg/s | 98,897µs | — |
| 8 | 1,928 msg/s | 23,891µs | **4.0배** |
| 128 | 2,317 msg/s | 20,276µs | **4.8배** |

기다렸다 모으지 않는다. **지금 큐에 있는 것만 묶으므로** 한가할 때는 배치가 1이 되어 지연이 늘지 않고,
밀릴 때만 커진다.

| DB 워커 | 배치 | 처리량 | DB 커넥션 |
|---------|------|--------|----------|
| 24 | 1 | 2,174 msg/s | **24** |
| 4 | 32 | 2,205 msg/s | **4** |

**DB 커넥션 6개를 배치 하나로 대신할 수 있다.** 커넥션은 DB 쪽 자원을 쓰고 늘리기 어렵지만
배치는 요청을 모으는 것뿐이다.

감수하는 비용은 분명하다 — **하나가 실패하면 그 트랜잭션 전체가 되돌아간다.**

### 직접 SQL 대 저장 프로시저

| 작업 | 직접 SQL | 프로시저 | 차이 |
|------|---------|---------|------|
| `History` (읽기, 왕복 1회) | 137µs | 178µs | **24% 느림** |
| `Counter` (직접 5왕복 → 1회) | 9,178µs | 8,799µs | **4% 빠름** |

왕복 하나는 약 95µs 다. 그런데 커밋 한 번이 8.8ms 라서 묻힌다.
**프로시저는 왕복이 많은 트랜잭션에만 값어치가 있고, 단일 질의에 씌우면 손해다.**

질의 하나에 평균 8~9ms 가 걸린다. `INSERT` 한 번인데도 그렇다.
`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` 이라
**커밋마다 디스크 동기화가 두 번** 일어나기 때문이다. 측정을 위해 낮추지 않았다.

### DB 대기가 다른 요청을 막지 않는다

| 상황 | `Echo` 처리량 | `Echo` p50 |
|------|--------------|-----------|
| 평시 | 213,563 msg/s | 36µs |
| `Save` 64접속 부하 중 | 209,306 msg/s | 37µs |

조건 · 한계 · 설계 변경 이력은 [`docs/benchmark.md`](docs/benchmark.md) 에 있다.

## 빌드

```bat
git clone https://github.com/<user>/iocp-echo-server.git
cd iocp-echo-server

cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

MySQL 이 기본 경로에 없으면 지정한다.

```bat
cmake -B build -G Ninja -DMYSQL_ROOT="D:/MySQL/MySQL Server 8.4"
```

메모리 오류 추적이 필요하면 AddressSanitizer 를 켠다.
**`RelWithDebInfo` 로 쓴다** — `Debug` 는 `/RTC` 가 함께 붙어 충돌한다.

```bat
cmake -B build-asan -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DECHO_ENABLE_ASAN=ON
cmake --build build-asan
```

실행 시 `clang_rt.asan_dynamic-x86_64.dll` 이 PATH 에 있어야 한다
(`VC\Tools\MSVC\<버전>\bin\Hostx64\x64`).

## 준비

### 1. 스키마

```bat
mysql -h 127.0.0.1 -u root -p -e "CREATE DATABASE echodb DEFAULT CHARSET utf8mb4;"
mysql -h 127.0.0.1 -u root -p echodb < sql/001_schema.sql
mysql -h 127.0.0.1 -u root -p echodb < sql/002_procedures.sql
```

`config/db.ini` 의 `use_procedures` 로 DB 접근 경로를 고른다.
`0` 이면 직접 SQL, `1` 이면 저장 프로시저다. 두 경로는 같은 결과를 낸다.

### 2. 설정

`config/db.ini.sample` 을 `config/db.ini` 로 복사하고 접속 정보를 채운다.
`config/db.ini` 는 커밋되지 않는다.

> 서버 전용 계정을 만들고 **해당 스키마에만 권한을 준다.**
> 관리자 계정을 서버 설정에 넣으면 설정 실수 한 번이 다른 스키마까지 미친다.
>
> ```sql
> CREATE USER 'echo'@'localhost' IDENTIFIED BY '<비밀번호>';
> GRANT ALL PRIVILEGES ON echodb.* TO 'echo'@'localhost';
> ```

주요 설정은 다음과 같다. 전부 기본값이 있어 비워 두어도 동작한다.

| 구역 | 키 | 기본값 | 내용 |
|------|-----|--------|------|
| `mysql` | `worker_count` | 4 | DB 워커 수. 커넥션 풀 크기와 같다 |
| | `use_procedures` | 0 | 1 이면 저장 프로시저 경로를 쓴다 |
| | `dispatch` | static | 워커 배정. `static`(해시 고정) 또는 `dynamic`(처리 중인 키 회피) |
| | `request_timeout_ms` | 3000 | 요청 하나에 주는 시간. 넘기면 질의를 시작하지 않는다. 0 이면 기한 없음 |
| | `batch_size` | 1 | 한 트랜잭션에 묶을 `Save` 최대 건수. 1 이면 묶지 않는다 |
| `server` | `io_worker_count` | 0 | 0 이면 코어수/2 (하한 2 · 상한 4) |
| | `game_lane_count` | 0 | 게임 서비스를 그 안에서 다시 나누는 수. 0 이면 1. 채팅 서비스는 1 로 고정 |
| | `max_connections` | 8192 | 동시 접속 상한. 넘어선 접속은 곧바로 끊는다. 0 이면 무제한 |
| | `inbound_queue_cap` | 8192 | 서비스 수신 큐 상한 |
| | `inbound_full_policy` | reject | 큐가 찼을 때. `reject`(오류 응답) 또는 `backpressure`(수신을 멈춰 상대를 늦춤) |
| | `message_rate_limit` | 0 | 연결당 초당 메시지 상한. 0 이면 제한 없음 |
| | `message_burst` | 0 | 잠깐 몰리는 몫. 0 이면 상한과 같게 둔다 |
| | `send_buffer_limit_kb` | 256 | 연결당 송신 누적 상한. 넘으면 끊는다. 0 이면 제한 없음 |
| | `send_mode` | notify | 발행 주체. `notify`(워커가 발행) 또는 `direct`(보내는 쪽이 발행) |
| | `admin_port_required` | 0 | 1 이면 관리 포트를 열지 못했을 때 기동을 멈춘다 |
| | `session_table_guard` | owner | 세션 표 보호. `owner`(소속 검사) 또는 `mutex`(잠금) |
| | `heartbeat_timeout_ms` | 30000 | 무응답 판정 시간 |
| | `shutdown_drain_ms` | 5000 | 종료 시 남은 일을 마칠 때까지 기다리는 상한 |
| | `admin_port` | 9100 | 관리 포트. 0 이면 열지 않는다 |
| `log` | `max_mb` | 64 | 이 크기를 넘거나 날짜가 바뀌면 파일을 넘긴다 |
| | `keep_files` | 10 | 넘긴 파일의 보관 개수 |

## 실행

```bat
build\bin\echo_server.exe
build\bin\echo_server.exe --config config\db.ini --port 9000
```

다른 창에서 봇을 붙인다. **봇도 서버와 같은 네트워크 계층을 쓴다.**

```bat
:: 부하 - echo / save / counter
build\bin\echo_bot.exe --connections 500 --seconds 30 --message echo

:: 저장 후 조회로 순서 · 내용 확인
build\bin\echo_bot.exe --mode verify

:: 같은 멱등성 키 재전송 - 값이 늘지 않아야 한다
build\bin\echo_bot.exe --mode idem

:: 접속 · 종료 반복 - 수명 관리 확인
build\bin\echo_bot.exe --connections 20 --churn 50
```

## 관리 포트

감시 도구와 로드밸런서가 볼 지점이다. 주 경로와 분리된 스레드에서 처리한다.

```
GET /health     200 ok  ·  503 unavailable
GET /metrics    200 수집 도구가 읽는 텍스트 형식
```

`/health` 가 정상 아님으로 답하는 경우는 두 가지다.
**종료 신호를 받은 뒤**(드레인이 도는 동안 로드밸런서가 미리 빼 가도록)와
**DB 워커가 하나도 붙지 못한 상태**다.

```
echo_connections 40
echo_messages_handled_total 3910368
echo_inbound_overflow_total 0
echo_messages_throttled_total 0
echo_db_expired_total 0
echo_db_queued 8
echo_db_workers_connected 4
echo_process_nanoseconds{quantile="0.5"} 610
echo_process_nanoseconds{quantile="0.99"} 3300
echo_process_nanoseconds_samples 1153303
echo_db_roundtrip_microseconds{quantile="0.99"} 43000
```

백분위는 마지막 기록 주기의 값이라 트래픽이 없으면 0 이 된다.
그래서 **표본 수를 함께 내보낸다** — 이 값이 없으면 "빨랐던 것" 과 "잴 것이 없던 것" 을 구분할 수 없다.

## 프로토콜

메시지 7종. 프레임 형식과 오류 코드는 [`docs/protocol.md`](docs/protocol.md) 에 있다.

| 메시지 | 서비스 | 경로 |
|--------|--------|------|
| `Echo` | 게임 | 서비스 스레드에서 즉시 반환. DB 미접촉 기준선 |
| `Save` | 게임 | 게임 → DB 워커 → 응답 큐 → 게임 |
| `History` | 게임 | 세션의 최근 N건 조회 |
| `Counter` | 게임 | 트랜잭션 + 멱등성 키 + 낙관적 동시성 제어 |
| `Ping` / `Pong` | — | 네트워크 계층에서 소비 |
| `Chat` / `ChatPush` | 채팅 | 요청 하나가 접속자 전원에게 나간다 |
| `Error` | — | 오류 코드 전달 |

## 알려진 한계

| 한계 | 내용 |
|------|------|
| 플랫폼 | 완료 통보 방식이 Windows 전용이다. 다른 계열은 수거 계층 교체가 필요하다 |
| 서비스 2개 | 라우팅 · 서비스별 큐 · 서비스 간 전달 · 브로드캐스트가 드러나는 최소 구성이다 |
| 한 세션의 여러 기능 | 서로 다른 스레드에서 돈다. 세션 상태를 어느 서비스가 갱신하는지 정해야 한다 |
| 레인 부하 분산 | 식별자를 나눈 정적 배분이다. 무거운 연결이 한 레인에 몰릴 수 있다 |
| 브로드캐스트 대상 | 접속하면 전원이 채팅 목록에 들어간다. 방·채널 개념을 두지 않았다 |
| DB 부하 분산 | `static` 은 정적이라 키가 적으면 워커가 논다. `dynamic` 은 배정마다 잠금을 잡는다 |
| 버퍼 상한 | 받는 본문 1KB · 수신 버퍼 16KB · 송신 누적 256KB. 이를 넘는 단일 메시지는 별도 전송 경로가 필요하다 |
| 상한과 메모리 | 서버 전체 최악값은 `max_connections × (수신 16KB + 송신 상한)` 이다. 두 값을 함께 정해야 한다 |
| 순서 보존 | 보존 단위가 연결 하나다. 서로 다른 연결 간 도착 순서는 보장하지 않는다 |
| 종료 대기 | 드레인 상한을 넘긴 요청은 `Unavailable` 로 응답하고 내려간다 |
| 측정 조건 | 서버와 봇이 같은 장비다. 별도 장비에서 재면 값이 달라진다 |
